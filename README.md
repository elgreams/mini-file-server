# Mini File Server (Login + Role-Based Uploads)

This project provides a minimal Flask application with login, role-gated uploads
and per-user storage.

## Getting Started

### Clone the repository

```bash
git clone <repo-url>
cd vibe-file-server
```

### Quick-start script

Use the helper script to bootstrap a virtual environment, install dependencies
and start the development server:

```bash
./scripts/run.sh
```

### Manual setup

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r app/requirements.txt
export APP_SECRET_KEY=$(openssl rand -hex 32)
python app/app.py
```

To serve the development server over HTTPS, provide certificate and key paths:

```bash
SSL_CERT_FILE=cert.pem SSL_KEY_FILE=key.pem python app/app.py
```

## Testing

```bash
source .venv/bin/activate
pip install -r app/requirements.txt pytest
pytest
```

## User Management

Use `user_admin.py` to manage accounts in the SQLite database.

The database is stored at `.vibe-data/app.db` within the project directory so
command-line tools and the running server share the same file even in different
environments (e.g., host vs. container). Set the `VIBE_DB_PATH` environment
variable to move it elsewhere.

The application server reads the same `VIBE_DB_PATH`. Ensure the variable points
to the **same** path when launching the server and when running
`user_admin.py`; otherwise the script may write to a different database and the
server will report "Invalid username or password" at login.

```bash
export VIBE_DB_PATH=/opt/vibe-file-server/.vibe-data/app.db
python app/app.py                # start the server
python app/user_admin.py list    # manage users in the same database
```

Create a user (you'll be prompted for a password). Newly created users must
change this password on first login unless the `--no-must-change-password` flag
is provided:

```bash
python app/user_admin.py add alice --can-upload
# or allow the initial password to remain:
python app/user_admin.py add bob --no-must-change-password
```

If a username already exists, reset the password with `passwd` or delete the
user and add them again. To force an existing account to pick a new password on
their next login, toggle the flag directly:

```bash
python app/user_admin.py set-must-change alice y
```

Pass `n` instead of `y` to clear the flag after the user updates their
credentials.

List existing users:

```bash
python app/user_admin.py list
```

Toggle upload permissions or delete a user:

```bash
# disable uploads
python app/user_admin.py set-upload alice n
# remove user entirely
python app/user_admin.py delete alice
```

Change a user's password:

```bash
python app/user_admin.py passwd alice
```

An older helper script, `create_user.py`, remains available for quick user
creation.

## Login Verification

Each login request must include a small proof-of-work token generated by the
application. The browser computes this token before submitting the form. In
addition, repeated failed attempts from the same IP trigger a temporary ban,
similar to fail2ban, discouraging brute‑force bots without burdening legitimate
users.

## Favicon

Place a `favicon.ico` file in `app/static/` to set a custom browser icon. It
will be served automatically at `/favicon.ico` and included on all pages.

## Production Deployment

The outline below shows one way to run the application on a VPS with a public
IP. Adjust paths and commands to match your environment.

1. **Clone and install** on the server:

   ```bash
   git clone <repo-url> /opt/vibe-file-server
   cd /opt/vibe-file-server
   python3 -m venv .venv
   . .venv/bin/activate
   pip install -r app/requirements.txt
   export APP_SECRET_KEY=$(openssl rand -hex 32)
   ```

2. **Run Gunicorn** bound to the VPS's public interface (example uses port 8000
   for HTTP):

   ```bash
   . .venv/bin/activate
   gunicorn -w 4 -b 0.0.0.0:8000 app.app:app
   ```

3. **Open the firewall** so external clients can reach the service. With
   `iptables` this might look like:

   ```bash
   sudo iptables -I INPUT -p tcp --dport 8000 -j ACCEPT
   ```

   Persist the rule according to your distribution's tooling (e.g.,
   `iptables-save` or `netfilter-persistent`).

4. **Enable HTTPS**. Obtain a certificate (for example, via Let's Encrypt) and
   launch Gunicorn with it:

   ```bash
   sudo apt install certbot
   sudo certbot certonly --standalone -d yourdomain.com
   sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
   sudo .venv/bin/gunicorn -w 4 -b 0.0.0.0:443 \
     --certfile /etc/letsencrypt/live/yourdomain.com/fullchain.pem \
     --keyfile /etc/letsencrypt/live/yourdomain.com/privkey.pem \
     app.app:app
   ```

   Replace `yourdomain.com` with your actual domain. Certificate files in
   `/etc/letsencrypt/live/<domain>/` are readable only by root, so the
   `gunicorn` command uses `sudo` with the virtual environment's binary. You may
   also terminate TLS with a reverse proxy such as Nginx and forward plain HTTP
   traffic to Gunicorn.

5. **Optional: create a `systemd` service** to keep Gunicorn running and
   restart automatically on failure.

These steps provide a basic production setup. For a hardened deployment, consider
rotating secrets and restricting file upload permissions.
